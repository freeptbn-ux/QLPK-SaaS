# Báo cáo Phân tích Hiệu năng (Performance Analysis Report) - QLPK SaaS

Báo cáo này trình bày các vấn đề về hiệu năng được tìm thấy trong codebase QLPK-SaaS, tập trung vào Next.js 15, React 19, Supabase và Framer Motion.

## 1. Tóm tắt tổng quan (Executive Summary)
Ứng dụng QLPK-SaaS có kiến trúc hiện đại nhưng đang gặp một số vấn đề về "render thrashing" ở frontend và xử lý dữ liệu chưa tối ưu ở server actions. Đặc biệt, các hiệu ứng animation đang chiếm dụng nhiều CPU không cần thiết.

## 2. Các vấn đề nghiêm trọng (Critical Issues)

### 2.1. Render Loop trong Animation (`CountUp.tsx`)
- **Vấn đề**: Thành phần `CountUp` sử dụng hàm `animate` của Framer Motion để cập nhật state React (`setCount`) liên tục trong mỗi frame (60fps). 
- **Hệ quả**: Gây ra hàng trăm lần re-render cho component cha (Dashboard) mỗi khi số liệu thay đổi. CPU tăng cao đột ngột trên các thiết bị yếu.
- **Giải pháp**: Sử dụng `useMotionValue` kết hợp với `useTransform` và `motion.span` để cập nhật trực tiếp vào DOM mà không thông qua React re-render.

### 2.2. Xử lý dữ liệu nặng trong Server Actions (`patients.ts`)
- **Vấn đề**: Hàm `getMedicineUsageByPatient` lấy toàn bộ dữ liệu thô từ database sau đó dùng JavaScript (`map`, `filter`, `reduce`) để tổng hợp.
- **Hệ quả**: Latency cao khi số lượng đơn thuốc của một bệnh nhân tăng lên. Tốn RAM của server.
- **Giải pháp**: Chuyển logic tổng hợp (Aggregation) vào Postgres thông qua một SQL Function hoặc View.

---

## 3. Phân tích Tầng Dữ liệu & Supabase

### 3.1. Truy vấn chưa tối ưu (Over-fetching)
- **Vấn đề**: Nhiều action sử dụng `select('*')` thay vì chọn các cột cần thiết.
- **Hệ quả**: Tăng kích thước payload trả về từ database và qua network.
- **Ví dụ**: `getPatientsPaginated` và `getAllMedicines` lấy toàn bộ các trường text dài ngay cả khi chỉ hiển thị danh sách.

### 3.2. Thiếu Cache ở một số API tĩnh
- **Vấn đề**: Danh sách thuốc (`getAllMedicines`) được gọi lại liên tục khi người dùng tìm kiếm trong đơn thuốc.
- **Giải pháp**: Sử dụng React `cache()` hoặc Next.js `unstable_cache` cho các dữ liệu ít thay đổi này.

---

## 4. Phân tích Frontend & React 19

### 4.1. Massive Components (`PrescriptionHistory.tsx`)
- **Vấn đề**: Component này chứa quá nhiều logic (sorting, filtering, pagination, modal states).
- **Hệ quả**: Mỗi khi một trạng thái nhỏ thay đổi (ví dụ: mở dropdown), toàn bộ danh sách đơn thuốc bị tính toán lại.
- **Giải pháp**: Tách nhỏ thành các sub-components: `PrescriptionItem`, `MedicineTable`, `HistoryFilters`.

### 4.2. Lạm dụng Client Components
- **Vấn đề**: Nhiều component lớn được đánh dấu `'use client'` trong khi có thể tách phần UI tĩnh ra Server Components.
- **Ví dụ**: Toàn bộ `StatisticsClient` là client component, khiến bundle size tăng.

---

## 4. Phân tích Animation & UI (Framer Motion)

### 4.1. Layout Thrashing
- **Vấn đề**: Sử dụng `layout` prop của Framer Motion trên các danh sách lớn mà không có `layoutScroll`.
- **Hệ quả**: Trình duyệt phải tính toán lại hình học của toàn bộ trang khi một item thay đổi kích thước.

---

## 5. Danh sách đề xuất ưu tiên (Prioritized Recommendations)

| Ưu tiên | Hạng mục | Mô tả giải pháp |
|:---:|---|---|
| 🔥 **Cao** | Tối ưu CountUp | Chuyển sang `useMotionValue` để tránh re-render Dashboard. |
| 🔥 **Cao** | SQL Aggregation | Viết RPC `get_patient_medicine_usage` để thay thế JS logic. |
| ⚡ **Trung** | Column Whitelisting | Thay `select('*')` bằng danh sách cột cụ thể trong tất cả actions. |
| ⚡ **Trung** | Component Splitting | Tách nhỏ `PrescriptionHistory` và `PatientFormDialog`. |
| 🍃 **Thấp** | Data Caching | Áp dụng `unstable_cache` cho danh sách thuốc và cài đặt phòng khám. |

## 6. Kết luận
Việc tối ưu hóa `CountUp` và chuyển logic aggregation vào database sẽ mang lại cải thiện hiệu năng rõ rệt nhất (>50% cảm giác mượt mà). Các bước tiếp theo nên tập trung vào việc tinh gọn bundle size thông qua component decomposition.
